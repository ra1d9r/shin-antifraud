## 1. Цель системы

Система анализирует финансовую транзакцию, рассчитывает вероятность мошенничества,
преобразует её в **Risk Score (0–100)** и принимает автоматическое решение:

| Decision | Смысл |
|---|---|
| `APPROVE` | транзакция разрешена |
| `CHALLENGE` | требуется дополнительная проверка / 2FA |
| `BLOCK` | транзакция заблокирована |

После каждого решения система обязана показать **объяснение**, почему транзакция
получила такой уровень риска.

**Главный сценарий (end-to-end):**

```
Transaction
  -> Feature Engineering
    -> ML Model
      -> Risk Score
        -> Risk Engine
          -> Decision
            -> XAI Explanation
```

## 2. Компоненты к реализации

### 2.1 Backend

- Стек: **Python + FastAPI**.
- Обязательные REST-эндпоинты:

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/predict` | принять транзакцию, выполнить feature engineering, ML, Risk Score, решение, вернуть причины риска |
| `GET` | `/health` | проверка работоспособности API |
| `GET` | `/stats` | базовая статистика по обработанным транзакциям |

- Обязателен **Swagger / OpenAPI**, чтобы транзакции можно было тестировать вручную
  без отдельного клиента.

## 4. Feature Engineering

Отдельный модуль (**не смешивать с API-кодом**). Минимальный набор признаков:

1. отклонение суммы от обычной суммы клиента;
2. необычная страна;
3. новый device;
4. изменение IP;
5. необычная частота транзакций;
6. резкое изменение геолокации;
7. время транзакции;
8. количество транзакций за определённый период;
9. другие разумные поведенческие признаки.

---

## 5. Machine Learning

Отдельный ML pipeline. Обязательные шаги:

1. Демонстрационный датасет ~ **100 000 транзакций**.
2. Формирование target `fraud / non-fraud`.
3. Preprocessing.
4. Разделение на train/test.
5. Обучение модели классификации мошенничества.

**Предпочтительно:** XGBoost или LightGBM.
**Fallback (при проблемах установки):** scikit-learn RandomForest / GradientBoosting.

**Жёсткие требования:**

- запрещена случайная заглушка вместо ML;
- модель реально обучается;
- обученная модель сохраняется на диск;
- отдельный training script;
- метрики: **precision, recall, F1, ROC-AUC**;
- учтён дисбаланс классов;
- API загружает сохранённую модель при старте.

---

## 6. Risk Score

ML probability преобразуется в Risk Score `0–100`.

Базовые пороги:

| Диапазон | Decision |
|---|---|
| 0–30 | `APPROVE` |
| 31–70 | `CHALLENGE` |
| 71–100 | `BLOCK` |

Требования:

- пороги **конфигурируемые** через отдельный config;
- бизнес-логика **не зашивается** в endpoint.

---

## 7. Explainable AI (XAI)

Отдельный XAI-модуль. SHAP или иной подход, объясняющий решение модели.

Для каждой транзакции показывать:

- Risk Score;
- Decision;
- **3–5 основных факторов риска**;
- влияние каждого фактора.

Пример вывода:

```
Risk Score: 87
Decision: BLOCK
Reasons:
  - Transaction amount is significantly higher than user's normal amount
  - New device detected
  - Unusual country
  - High transaction frequency
```

## 8. Dashboard

Простой современный web dashboard (React + Vite).

### 8.1 Overview
- количество транзакций;
- количество подозрительных;
- количество заблокированных;
- средний Risk Score;
- fraud rate.

### 8.2 Transactions

Таблица: `Transaction ID | Amount | Country | Device | Risk Score | Decision`

Фильтрация по: `decision`, `risk score`, `country`, `fraud status`.

### 8.3 Transaction Simulator (обязательная часть)

Форма ручного ввода: `amount`, `country`, `device`, `IP`, `merchant`, `timestamp`,
`transaction frequency`, предыдущая сумма, предыдущая страна, геолокация.

Кнопка **«Analyze Transaction»** отправляет `POST /predict` и отображает:

- Risk Score;
- Decision;
- Risk level;
- Reasons;
- Feature contributions.

Система должна полностью hand-тестироваться через интерфейс.

## 9. Hand Testing — обязательные сценарии

| # | Сценарий | Вход | Ожидаемый результат |
|---|---|---|---|
| 1 | Normal transaction | обычная сумма, знакомый device, привычная страна, нормальная частота | низкий Risk Score / `APPROVE` |
| 2 | New device | обычная транзакция, новый device | Risk Score увеличивается |
| 3 | Unusual country | транзакция из непривычной страны | повышенный риск |
| 4 | Large amount | сумма значительно выше обычной | повышенный риск |
| 5 | Multiple anomalies | большая сумма + новый device + необычная страна + высокая частота | высокий Risk Score / `BLOCK` |

**Важно:** тесты должны демонстрировать **изменение** Risk Score при изменении
входных параметров.

## 10. Business Cost

Модуль оценки бизнес-стоимости решений:

- **Fraud Loss** — стоимость пропущенного мошенничества;
- **Customer Inconvenience** — стоимость ложных блокировок / лишних проверок.

На Dashboard: график или summary по `Fraud Loss`, `Customer Inconvenience`, `Total Cost`.
Плюс возможность **менять thresholds** и видеть влияние на показатели.

## Отклонения и решения

Здесь фиксируются все инженерные решения, отличающиеся от буквы ТЗ, и их причина.

| # | Пункт ТЗ | Решение | Причина |
|---|---|---|---|
| D-1 | §11 структура | `backend/app/models/` переименован в `backend/app/schemas/` (Pydantic-модели), ML-артефакты лежат в `backend/models/` | слово *models* перегружено: Pydantic-схемы это не ML-модели. Разделение убирает путаницу |
| D-2 | §5 ML | автоматически выбирается LightGBM, при его отсутствии — sklearn `HistGradientBoosting`; `GradientBoosting` доступен флагом `--algorithm`. Фактически установлен LightGBM 4.7.0 | среда Python 3.14: бинарные колёса LightGBM/XGBoost могут отсутствовать. Fallback гарантирует запуск на любой машине |
| D-3 | §7 XAI | SHAP это опциональная зависимость. При её отсутствии работает собственный explainer (вклады признаков + правила). Фактически установлен SHAP 0.52.0 | SHAP тянет компилируемые расширения; прототип обязан запускаться без них |
| D-7 | §5 ML | вероятности калибруются методом sigmoid на отдельной части выборки | Risk Score = probability × 100. Взвешивание классов завышает вероятности, а изотоническая калибровка на этой задаче вырождается в ступеньку 0/100 и делает полосу CHALLENGE недостижимой |
| D-4 | §3 данные | добавлены опциональные поля профиля клиента (`user_avg_amount`, `user_home_country`, `known_device_ids`, `previous_ip_address`, `previous_timestamp`, `previous_latitude`, `previous_longitude`) | без истории клиента невозможно посчитать «отклонение от обычного поведения» из §4. Поля опциональные: при отсутствии берутся из in-memory профиля |
| D-5 | §2 API | добавлены вспомогательные эндпоинты (`/transactions`, `/scenarios`, `/business-cost`, `/config/thresholds`) | нужны Dashboard (§8) и Business Cost (§10); обязательные три эндпоинта сохранены без изменений |
| D-6 | §13 Docker | Docker в среде разработки недоступен (`docker: command not found`), файлы написаны, но `docker compose up` локально не прогонялся | ограничение машины; локальный запуск без Docker полностью рабочий |
