## 1. Цель системы

Система анализирует финансовую транзакцию, рассчитывает вероятность мошенничества,
преобразует её в **Risk Score (0–100)** и принимает автоматическое решение:

| Decision | Смысл |
|---|---|
| `APPROVE` | транзакция разрешена |
| `CHALLENGE` | требуется дополнительная проверка / 2FA |
| `BLOCK` | транзакция заблокирована |

После каждого решения система обязана показать **объяснение**, почему транзакция
получила такой уровень риска.

**Главный сценарий (end-to-end):**

```
Transaction
  -> Feature Engineering
    -> ML Model
      -> Risk Score
        -> Risk Engine
          -> Decision
            -> XAI Explanation
```

## 4. Feature Engineering

Отдельный модуль (**не смешивать с API-кодом**). Минимальный набор признаков:

1. отклонение суммы от обычной суммы клиента;
2. необычная страна;
3. новый device;
4. изменение IP;
5. необычная частота транзакций;
6. резкое изменение геолокации;
7. время транзакции;
8. количество транзакций за определённый период;
9. другие разумные поведенческие признаки.

---

## 5. Machine Learning

Отдельный ML pipeline. Обязательные шаги:

1. Демонстрационный датасет ~ **100 000 транзакций**.
2. Формирование target `fraud / non-fraud`.
3. Preprocessing.
4. Разделение на train/test.
5. Обучение модели классификации мошенничества.

**Предпочтительно:** XGBoost или LightGBM.
**Fallback (при проблемах установки):** scikit-learn RandomForest / GradientBoosting.

**Жёсткие требования:**

- запрещена случайная заглушка вместо ML;
- модель реально обучается;
- обученная модель сохраняется на диск;
- отдельный training script;
- метрики: **precision, recall, F1, ROC-AUC**;
- учтён дисбаланс классов;
- API загружает сохранённую модель при старте.

---

## 6. Risk Score

ML probability преобразуется в Risk Score `0–100`.

Базовые пороги:

| Диапазон | Decision |
|---|---|
| 0–30 | `APPROVE` |
| 31–70 | `CHALLENGE` |
| 71–100 | `BLOCK` |

Требования:

- пороги **конфигурируемые** через отдельный config;
- бизнес-логика **не зашивается** в endpoint.

---

## 7. Explainable AI (XAI)

Отдельный XAI-модуль. SHAP или иной подход, объясняющий решение модели.

Для каждой транзакции показывать:

- Risk Score;
- Decision;
- **3–5 основных факторов риска**;
- влияние каждого фактора.

Пример вывода:

```
Risk Score: 87
Decision: BLOCK
Reasons:
  - Transaction amount is significantly higher than user's normal amount
  - New device detected
  - Unusual country
  - High transaction frequency
```

## 9. Hand Testing — обязательные сценарии

| # | Сценарий | Вход | Ожидаемый результат |
|---|---|---|---|
| 1 | Normal transaction | обычная сумма, знакомый device, привычная страна, нормальная частота | низкий Risk Score / `APPROVE` |
| 2 | New device | обычная транзакция, новый device | Risk Score увеличивается |
| 3 | Unusual country | транзакция из непривычной страны | повышенный риск |
| 4 | Large amount | сумма значительно выше обычной | повышенный риск |
| 5 | Multiple anomalies | большая сумма + новый device + необычная страна + высокая частота | высокий Risk Score / `BLOCK` |
| 6 | **High frequency** | всплеск числа операций при прочих привычных параметрах | повышенный риск |

Сценарий 6 добавлен ревизией от 2026-09-17: он нужен кнопке **High Frequency**
в тестовом интерфейсе (§8.4). Изолирует признак частоты — остальные параметры
остаются обычными.

**Важно:** тесты должны демонстрировать **изменение** Risk Score при изменении
входных параметров.

Все сценарии описывают **одного клиента**: меняется ровно то, что заявлено
в названии. Иначе сравнивать Risk Score между ними бессмысленно.

## 15-ter. Фактический контракт `POST /predict`

Frontend подстраивается под **существующий** ответ, а не наоборот.

**Запрос** — обязательны 14 полей [ТЗ §3](#3-данные-транзакции).
`transaction_id` и `timestamp` можно не передавать: первый генерируется,
второй берётся как текущее время UTC.

Опционально принимается контекст клиента (`user_avg_amount`,
`user_amount_std`, `user_home_country`, `user_typical_frequency`,
`known_device_ids`, `previous_ip_address`, `previous_timestamp`,
`previous_latitude`, `previous_longitude`, `txn_count_last_hour`,
`merchant_category`) и флаг `persist`.

**Запрос отвергается с HTTP 422**, если данные противоречат сами себе:
`previous_timestamp` позже `timestamp`, а при пустом `timestamp` — позже
момента обработки. Сравнение идёт после приведения к UTC, поэтому время
с указанной зоной обрабатывается корректно.

**Нормализуется**, а не отвергается, ноль в счётчиках операций
(`transaction_frequency`, `txn_count_last_hour`): он приводится к единице
— см. [D-11](#отклонения-и-решения).

**Ответ:**

| Поле | Смысл |
|---|---|
| `risk_score` | 0–100, итоговая оценка после политик |
| `model_score` | 0–100, оценка только модели |
| `probability` | вероятность фрода |
| `decision` | `APPROVE` / `CHALLENGE` / `BLOCK` |
| `risk_level` | `LOW` / `MEDIUM` / `HIGH` / `CRITICAL` |
| `raised_by_rules` | подняли ли политики оценку выше модели |
| `triggered_rules[]` | `key`, `title`, `min_score` |
| `explanation.reasons[]` | причины строками — сначала политики, затем факторы |
| `explanation.factors[]` | `feature`, `value`, `display_value`, `contribution`, `direction`, `reason`, `description` |
| `explanation.method` | `shap` / `lightgbm_native` / `ablation` |
| `explanation.units` | `logit` или `probability` — в чём измерен вклад |
| `thresholds` | `approve_max`, `challenge_max`, `critical_min` |
| `features` | полный вектор из 27 признаков |
| `processing_ms` | время обработки на сервере |

| # | Пункт ТЗ | Решение | Причина |

| D-10 | §8.2 форма | форма содержит 14 полей ТЗ §3, но интерфейс дополнительно отправляет контекст клиента из выбранного сценария | без контекста повторные нажатия Analyze дают разные ответы: профиль клиента накапливается между запросами, и устройство перестаёт быть новым. Для инструмента ручной проверки это выглядело бы как дефект |
| D-7 | §5 ML | вероятности калибруются методом sigmoid на отдельной части выборки | Risk Score = probability × 100. Взвешивание классов завышает вероятности, а изотоническая калибровка на этой задаче вырождается в ступеньку 0/100 и делает полосу CHALLENGE недостижимой |
| D-4 | §3 данные | добавлены опциональные поля профиля клиента (`user_avg_amount`, `user_home_country`, `known_device_ids`, `previous_ip_address`, `previous_timestamp`, `previous_latitude`, `previous_longitude`) | без истории клиента невозможно посчитать «отклонение от обычного поведения» из §4. Поля опциональные: при отсутствии берутся из in-memory профиля |
| D-5 | §2 API | добавлены вспомогательные эндпоинты: `/model`, `/transactions`, `/scenarios`, `/scenarios/{key}`, `/scenarios/{key}/run`, `/analytics/overview`, `/transactions/{id}/feedback`, `/feedback`, `/feedback/summary`, `/monitoring/drift`, `/monitoring/shadow` | нужны дашборду (§8) и ручной проверке (§9); обязательные три эндпоинта сохранены без изменений. **Исправлено 2026-09-19:** прежняя редакция обещала `/business-cost` и `/config/thresholds`, которых в коде никогда не было — Business Cost считается внутри `/analytics/overview`, а пороги задаются конфигурацией |
| D-11 | §3 счётчики | ноль в `transaction_frequency` и `txn_count_last_hour` приводится к единице | в обучающих данных счётчик считался после добавления операции в ленту, поэтому его минимум там равен 1, а нулей нет вовсе (0 % строк). Ноль на входе — значение вне обучающего распределения. Отвергать его было бы грубо: клиент вправе прочитать поле как «операций до текущей», поэтому значение нормализуется. Приведение живёт в общем для обучения и инференса коде (`features/builder.py`), иначе договорённость разошлась бы между двумя путями |
| D-13 | §8, §10 аналитика | расчёт по датасету выгружается в артефакт `backend/models/evaluation.json`, а не считается в запросе | полный проход по 100 000 транзакций занимает около двадцати секунд: признаки строятся построчно ради отсутствия training/serving skew, а предельный вклад каждой политики требует отдельного прогона движка. Ни старт приложения, ни обработчик запроса столько ждать не могут. Тот же приём, что с `model_metrics.json` |
| D-12 | §3 данные | запрос, где `previous_timestamp` позже `timestamp`, отвергается с HTTP 422 | раньше противоречие принималось молча: отрицательный интервал зажимался в ноль, и ответ показывал скорость перемещения, взявшуюся из ниоткуда, при HTTP 200. Проверка стоит на границе API, а не в feature engineering: туда `previous_timestamp` может прийти из накопленного профиля, где «предыдущая позже текущей» означает законную запоздавшую транзакцию, которую обязаны обработать |
| D-14 | сверх ТЗ | добавлена обратная связь аналитика: отметка вердикта верным или ошибочным, накопление настоящих меток на диске | ТЗ описывает систему, которая выносит решения, но не узнаёт их исход. Из-за этого единственные метрики качества в проде — самооценка: `GET /stats` считает `fraud_rate` по собственным вердиктам и честно оговаривает, что это не измеренная истина. Отметка аналитика — единственный канал, по которому в работающую систему попадает правда; из накопленного получаются подтверждённая точность и заготовка обучающей выборки следующего цикла. Хранится на диске, потому что это единственное в системе, что нельзя пересчитать заново |
| D-15 | сверх ТЗ | добавлено наблюдение за сдвигом распределения признаков (PSI живого потока против обучающего) | ТЗ описывает систему, которая обучается один раз и дальше отвечает. Но когда входные данные перестают походить на обучающие, оценки модели становятся недостоверными, а система об этом молчит: исключения нет, в логах пусто, ответ по-прежнему число от 0 до 100. Это единственная поломка в проекте, которую нельзя заметить ни тестом, ни healthcheck'ом — только сравнением распределений. Мера PSI выбрана за то, что считается по корзинам и не требует хранить наблюдения: в памяти живут триста счётчиков независимо от объёма трафика |
| D-16 | сверх ТЗ | добавлен теневой режим: вторая конфигурация Risk Engine на том же потоке, её решения никуда не уходят | дашборд показал, что текущий порог далеко от самого дешёвого, а четыре политики из шести приносят одно трение. Но кривая отвечает, что было бы на обучающем датасете, а решать надо про сегодняшний поток — и трогать работающую систему ради проверки гипотезы нельзя. Тень отвечает на тот же вопрос без риска: те же операции, второе решение, никаких последствий. Обошлось почти бесплатно, потому что движок с самого начала принимает пороги объектом, а признаки и прогон модели к этому моменту уже посчитаны |
| D-6 | §13 Docker | Docker в среде разработки недоступен (`docker: command not found`), поэтому локально `docker compose up` не запускался. Схема сети была проверена заглушкой nginx на Python: продакшн-бандл, отрезание префикса `/api`, все шесть сценариев. **Снято:** сборка и живой стек проверяются в CI (`.github/workflows/ci.yml`, задача `docker`) на каждый push — образы собираются, healthcheck ждёт загрузки модели, запросы идут через nginx на backend | ограничение машины обойдено там, где Docker есть |
