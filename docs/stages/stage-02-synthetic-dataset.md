# Этап 02 — Synthetic dataset

**Статус:** `DONE`
**Дата:** 2026-09-17
**Пункты ТЗ:** §5.1 (датасет ~100 000), §5.2 (target fraud/non-fraud)

---

## Цель

Демонстрационный датасет на ~100 000 транзакций, на котором модель учится
**поведению**, а не артефактам генератора.

---

## Ключевое решение: данные порождаются, а не размечаются

Наивный подход — сгенерировать случайные строки и пометить часть из них
`is_fraud=1` — даёт датасет, на котором любая модель показывает ROC-AUC ≈ 1.0,
потому что метка ни с чем не связана либо связана слишком прямо. На демонстрации
такая система разваливается от первой же нестандартной транзакции.

Здесь порядок обратный:

```
1. Профили клиентов        ->  кто такой клиент: домашняя страна, обычная сумма,
                               свои устройства, своя IP-подсеть, обычная частота
2. Хронологические ленты    ->  каждая транзакция знает о предыдущей
3. Сценарии атак            ->  фрод порождается механикой атаки
4. Обманки в легальных      ->  реальные поездки, новый телефон, крупная покупка
```

### Профиль клиента (`UserProfile`)

| Атрибут | Как задаётся |
|---|---|
| домашняя страна | взвешенный выбор, регион Центральной Азии как основной рынок |
| обычная сумма | логнормальное распределение, медиана ~50 USD, диапазон 8–900 |
| устройства | 1–3 устройства на клиента |
| IP-подсеть | первые три октета — «провайдер клиента» |
| обычная частота | 0.7–6.0 транзакций в сутки |
| возраст счёта | 88 % клиентов — от 90 дней; 12 % — молодые счета (3–60 дней) |
| любимые мерчанты | 3–6 повседневных; у 55 % снятие наличных, у 40 % крипта/ставки/переводы |

### Сценарии атак (`FraudScenario`)

| Сценарий | Механика | Длина эпизода |
|---|---|---|
| `account_takeover` | новое устройство (75 %) + новая сеть + чужая страна (70 %) + сумма ×1.2–8, чаще ночью | 2–6 |
| `card_testing` | прозвон карты: мелкие списания 0.8–9 USD с интервалом 30–180 с | 5–14 |
| `impossible_travel` | далёкая страна через 5–45 минут после домашней транзакции | 1–3 |
| `new_device_cashout` | вывод дома, но с незнакомого устройства, сумма ×2–10 | 1–4 |
| `amount_anomaly` | самый трудный случай: всё привычное, ненормальна только сумма (×4–15) | 1–2 |
| `new_account_abuse` | молодой счёт + новое устройство + сумма ×2.5–10 | 1–3 |

Сценарий и длина эпизода выбираются **одним решением**: длина специфична для
механики (прозвон карты — это десяток мелких списаний, вывод средств — одна-две
крупных операции).

### Обманки в легальных транзакциях

Без них классы разделяются тривиально, поэтому в легальный поток намеренно внесены:

| Обманка | Частота |
|---|---|
| реальная поездка (2–6 транзакций подряд в другой стране) | 1.5 % транзакций стартуют поездку |
| покупка нового телефона (новый `device_id`) | 3 % |
| смена провайдера / мобильная сеть (новая IP-подсеть) | 4 % |
| крупная законная покупка (×6–18 от обычной суммы) | 2 % |
| мелкая повседневная трата 1–12 USD (кофе, такси, подписка) | 12 % |
| законное пользование «рискованными» категориями | 16.6 % транзакций |

## Найденные и исправленные дефекты

Шесть дефектов. Первые три найдены **до** обучения модели, четвёртый — при
последующем аудите этапа, пятый — при первом обучении, шестой — при разборе
распределения сценариев. Каждый из них выглядел бы в CSV безобидно, но делал
данные или метрики недостоверными.

### 1. Нарушение хронологии ленты

Первая версия наращивала время шагами, а затем перезаписывала час суток
через `timestamp.replace(hour=...)` — чтобы получить дневной пик активности.
Результат: если шаг был 5 часов, а случайный «реалистичный» час оказывался
раньше, **время шло назад**. `previous_timestamp` становился позже текущей
транзакции, интервал получался отрицательным, а признаки скорости перемещения
и частоты — мусорными.

**Решение.** Моменты транзакций рисуются сразу целиком и сортируются
(`_draw_timeline_timestamps`). Монотонность, реалистичное распределение часов
и соблюдение границ окна получаются одновременно и по построению.

### 2. Транзакции за правой границей окна

Лента уходила до `2026-09-18` при `end_date = 2026-09-01`, из-за чего
`account_age_days` считался относительно несогласованной точки отсчёта.

**Решение.** Ширина окна выводится из объёма и активности клиентов:
`window_days = rows / (users × средняя частота)`, а моменты рисуются внутри окна.
Побочный эффект — приятный: `transaction_frequency` в данных теперь совпадает
с обычной частотой клиента из профиля, иначе признак «необычная частота»
учился бы на рассогласованных величинах.

### 3. Сценарий разыгрывался дважды

Сценарий выбирался один раз при выделении бюджета фрода (чтобы взять длину
эпизода) и **второй раз независимо** при генерации ленты. Длины не соответствовали
сценариям, распределение перекосилось: `account_takeover` занимал 70 % вместо 28 %.

**Решение.** Сценарий и длина выбираются один раз и передаются в ленту вместе.

### 4. Генерация не была воспроизводимой между запусками *(найдено при аудите)*

DoD этапа требовал детерминированности при фиксированном seed, и тест это
подтверждал. Тест лгал.

Сценарий `account_takeover` выбирал страну так:

```python
country = rng.choice(tuple(HIGH_RISK_COUNTRIES))   # HIGH_RISK_COUNTRIES — frozenset
```

Порядок обхода `set` и `frozenset` строк зависит от их хешей, а Python
рандомизирует хеш строк **в каждом процессе** (`PYTHONHASHSEED`). Поэтому
`tuple(frozenset)` давал разный порядок при каждом запуске, и один и тот же
seed порождал разные датасеты:

```
запуск 1: md5 570495356c94d7c14468a9a730770268
запуск 2: md5 c06b628125de8bdb1e3c6c470e895e35
```

Существовавший тест `test_generation_is_deterministic` этого не ловил, потому
что обе генерации выполнялись **в одном процессе** и делили один хеш-сид.

**Решение.** Источником выборки стал упорядоченный кортеж
`HIGH_RISK_COUNTRY_LIST`; множество осталось только для проверки
принадлежности. Добавлен тест `test_generation_is_deterministic_across_processes`,
который запускает генерацию в трёх подпроцессах с `PYTHONHASHSEED` 0, 1 и
424242 и сравнивает контрольные суммы.

### 5. Категория мерчанта была прямой уликой фрода *(найдено при обучении)*

Первая обученная модель дала ROC-AUC 0.9986 и вырожденное распределение
Risk Score: 19 492 транзакции в диапазоне 0–10, 359 в диапазоне 90–100 и
почти ничего между ними. Полоса `CHALLENGE` оказалась недостижимой, то есть
сценарии hand-testing из ТЗ §9 не показали бы постепенного роста риска.

Важность признаков указала на причину: `is_high_risk_merchant` давал вклад
+0.0926 — вдвое больше следующего признака. В генераторе фрод почти всегда
шёл на cashout-мерчантов (крипта, ставки, переводы, ATM), а легальные клиенты
ими почти не пользовались: **3 % против 49 %**. Модель выучила категорию
мерчанта вместо поведения.

**Решение — сделать данные честнее, а не подкручивать модель:**

| Изменение | Было | Стало |
|---|---|---|
| доля клиентов со снятием наличных в привычках | — | 55 % |
| доля клиентов с крипто / ставками / переводами | 18 % | 40 % |
| фрод уходит на cashout-мерчанта | почти всегда | 40–70 % в зависимости от сценария |
| мелкие повседневные траты у легальных (кофе, такси, подписки) | нет | 12 % транзакций |
| `account_takeover` всегда с нового устройства и из чужой страны | да | устройство новое в 75 %, страна чужая в 70 % |
| множители суммы у сценариев | 3–25x | 1.2–15x |

Результат после перегенерации:

| Показатель | Было | Стало |
|---|---|---|
| рискованная категория у легальных / у фрода | 3 % / 49 % | 16.6 % / 34.0 % |
| мелкая сумма (<10) у легальных / у фрода | 1 % / 46 % | 13.8 % / 37.3 % |
| `is_high_risk_merchant` в топе разделяющих признаков | 1-е место | выбыл из топ-10 |

### 6. Сценарий, которого не было в данных

`new_account_abuse` не встретился в выборке ни разу: вес 6 %, да ещё и отбрасывался
для 88 % клиентов со старыми счетами. Сценарий существовал в коде и в документации,
но модель не могла его выучить.

**Решение.** Сценарий привязан к возрасту счёта напрямую: для счёта моложе
60 дней он выбирается с вероятностью 45 %, для остальных исключён из розыгрыша.

## Валидация данных

`validate_dataset()` проверяет то, что глазами в CSV не увидеть:

- отсутствие пустых значений в обязательных колонках ТЗ §3;
- уникальность `transaction_id`, положительность сумм;
- `previous_timestamp < timestamp` для каждой строки;
- совпадение `previous_transaction_amount` с реальной предыдущей транзакцией клиента;
- соблюдение границ временного окна;
- долю фрода в разумном диапазоне и присутствие обоих классов.

Дополнительно скрипт **перечитывает записанный CSV и валидирует его заново** —
именно эта проверка поймала дефект с микросекундами в синтетической «нулевой»
транзакции, из-за которого колонка `previous_timestamp` не парсилась обратно
как дата и молча оставалась строкой.

### Разделимость классов

Средние значения признаков (все 1 924 мошеннических против 10 000 случайных легальных):

| Признак | Легальные | Фрод | Отношение |
|---|---|---|---|
| `travel_speed_kmh` | 134 | 34 951 | 260x |
| `geo_distance_km` | 108 | 3 984 | 37x |
| `is_high_risk_country` | 0.00 | 0.28 | 29x |
| `is_impossible_travel` | 0.01 | 0.62 | 26x |
| `country_changed_from_previous` | 0.03 | 0.67 | 17x |
| `is_high_frequency` | 0.01 | 0.21 | 13x |
| `amount_zscore` | 0.49 | 5.09 | 10x |
| `is_new_device` | 0.03 | 0.21 | 6x |

И, что важнее, **пересечение классов присутствует**:

- рискованная категория мерчанта встречается у **16.6 %** легальных транзакций;
- мелкая сумма (<10) — у **13.8 %** легальных;
- около четверти фрода проходит со знакомого устройства из домашней страны.

Это те самые случаи, на которых будут видны реальные precision и recall.
