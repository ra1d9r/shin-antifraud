## Решения

### Приложение поднимается даже без модели

Отсутствие артефакта не роняет старт. `/health` честно возвращает
`degraded`, `/predict` отвечает 503 с текстом «Выполните:
`python backend/scripts/train_model.py`».

Падение на старте выглядело бы строже, но было бы хуже: через API нельзя
было бы даже узнать, что именно не так. Проверено тестом
`test_health_degrades_without_model`.

### Профиль обновляется после принятия решения

Порядок здесь не косметический. Если записать транзакцию в профиль до
расчёта признаков, текущая операция сама себя объявит привычной, и признак
`is_new_device` не сработает **никогда**.

### Приоритет источников контекста

```
поле передано в запросе  ->  берём его
поля нет, клиент известен ->  берём из профиля
клиент новый              ->  нейтральное значение
```

Первый пункт сделан ради ручного тестирования. Если симулятор передаёт
контекст явно, повторный запрос с теми же данными даёт **тот же** ответ
независимо от накопленной истории. Без этого судья на демонстрации нажал бы
«Analyze» дважды и получил разные числа — что выглядело бы как дефект.

Оба поведения зафиксированы тестами: `test_explicit_context_makes_result_reproducible`
и `test_new_device_detected_against_learned_profile`.

### Режим «что если»

Флаг `persist: false` считает ответ, но не трогает историю и профиль.
Нужен странице Business Cost (этап 13), где один и тот же поток
пересчитывается при разных порогах, и полезен для экспериментов в Swagger.

### Доменные ошибки переводятся в HTTP в одном месте

Сервисы и ML-слой бросают `ShinError` и ничего не знают про коды ответов.
Единственный обработчик в `main.py` превращает их в JSON с
`error_code`, `message` и `details`. Ошибки валидации pydantic сжимаются
до пары «поле — причина», а не отдаются сырым деревом:

```json
{
  "error_code": "validation_error",
  "message": "Некорректные данные запроса",
  "details": {"errors": [{"field": "amount", "message": "Input should be greater than 0"}]}
}
```

### Фабрика вместо модуля-синглтона

Приложение собирается функцией `create_app(settings)`, состояние живёт в
`app.state.shin`. Тесты поднимают независимый экземпляр со своими
настройками — например, с несуществующим путём к модели — не трогая
глобальных переменных.

## Найденные дефекты

### 1. Логи API были нечитаемы

Под uvicorn на Windows консоль по умолчанию не UTF-8, и русскоязычные записи
превращались в мусор:

```
INFO | shin.api | ������ Shin Anti-Fraud System v1.0.0
```

CLI-скрипты вызывали `enable_utf8_output()` сами, а web-приложение — нет.
Вызов перенесён внутрь `configure_logging()`, то есть в единую точку
настройки логирования, и теперь работает везде.

### 2. Ложная тревога при осмотре маршрутов

Первая проверка показала, что `app.routes` содержит только служебные
маршруты, а `/predict` и `/health` отсутствуют. Выглядело как дефект сборки.

На деле в FastAPI 0.141 подключённый роутер представлен объектом
`_IncludedRouter`, а не копированием маршрутов в `app.routes`. Устарел
способ осмотра, а не приложение. Правильная проверка — по OpenAPI-схеме
и реальными запросами, так и сделано в тестах.

## Пример работы

Запрос: ночная операция на 2500 при обычных 100, из Нигерии, с незнакомого
устройства, через 22 минуты после операции в Казахстане.

```
Risk Score : 100  (модель дала 100)
Decision   : BLOCK, уровень CRITICAL
Политики   : impossible_travel, velocity_burst, high_risk_country,
             unusual_country, new_device
Причин     : 10, факторов модели: 5
Обработка  : ~6 мс
```

Полные запрос и ответ — в README, разделы 10 и 11.
