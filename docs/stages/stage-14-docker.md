## Решения

### Модель обучается на этапе сборки

Артефакты не лежат в репозитории: `.gitignore` исключает и датасет на 25 МБ,
и `.joblib`. Копировать в образ нечего, а без модели `/predict` отвечал бы 503.
Поэтому образ самодостаточен — внутри него генерируется датасет и обучается
модель.

Промежуточный CSV удаляется **в том же слое**, где создаётся:

```dockerfile
RUN python backend/scripts/generate_dataset.py \
    && python backend/scripts/train_model.py \
    && rm -f backend/data/raw/*.csv
```

Разнеси эти команды по разным `RUN` — и 25 МБ навсегда остались бы в истории
слоёв, даже будучи удалёнными в следующем.

### Браузер не видит сеть Docker

Главное решение этапа. Vite подставляет переменные окружения в бандл
**на этапе сборки**, а не при запуске контейнера. Если бы адрес API был
`http://backend:8000`, он попал бы в JavaScript, который исполняется
в браузере пользователя — а оттуда имя `backend` не резолвится. Интерфейс
молча не работал бы, причём только в Docker.

Поэтому `VITE_API_URL=/api`: запросы уходят на тот же origin, откуда
загружена страница, а nginx переправляет их в контейнер backend.

```
браузер ──/api/predict──► nginx (frontend:80) ──/predict──► backend:8000
```

Завершающий слэш в `proxy_pass http://shin_backend/;` отрезает префикс.
Без него backend получил бы `/api/predict` и ответил 404.

Побочная выгода: запросы становятся одноисточниковыми, и **CORS в этой
схеме не участвует вовсе**.

### libgomp1 обязателен

LightGBM тянет `libgomp.so.1`, которой на `python:*-slim` нет. Без пакета
`libgomp1` импорт падает уже на старте, причём с сообщением про
отсутствующий разделяемый объект, а не про LightGBM — искать причину
пришлось бы долго.

### Healthcheck проверяет готовность, а не живость

```dockerfile
CMD curl -fsS http://localhost:8000/health | grep -q '"model_loaded":true'
```

Процесс uvicorn поднимается за секунду, но `/predict` до загрузки модели
отвечает 503. Проверка на факт живости пропустила бы это состояние,
и `depends_on: service_healthy` перестал бы что-либо гарантировать.

### Непривилегированный пользователь

Рантайм работает от `shin` (uid 10001). Права root приложению не нужны,
а образ с процессом от root — лишний риск без всякой выгоды.

## Найденный дефект: моя же проверка солгала

Docker на машине нет, поэтому я проверял сборку фронтенда локально:

```bash
VITE_API_URL=/api npm run build
```

Сборка прошла. Но в бандле оказалось:

```js
const Uu = "C:/Program Files/Git/api".replace(/\/$/, "")
```

Git Bash на Windows преобразовал `/api` в Windows-путь — это подстановка
путей MSYS. Каждый запрос ушёл бы на `C:/Program Files/Git/api/predict`.

Опасность не в самой ошибке: в Docker сборка идёт на Linux, и там такого
не произойдёт. Опасность в том, что **проверка выглядела успешной**.
Сборка завершилась без ошибок, и если бы я не заглянул внутрь бандла,
то записал бы в отчёт «проверено».

Правильный запуск на Windows:

```bash
MSYS_NO_PATHCONV=1 VITE_API_URL=/api npm run build
```

После него в бандле то, что нужно:

```js
const Uu = "/api".replace(/\/$/, "")
```

## Что проверено и что нет

**Docker на машине разработки отсутствует** (`docker: command not found`),
поэтому `docker compose up --build` **не прогонялся**. Это зафиксировано
как [D-6](../TZ.md#отклонения-и-решения) ещё на этапе 01.

Чтобы оговорка не превратилась в «написал и не проверил», схема Docker-сети
проверена без Docker: поднят Python-сервер, повторяющий поведение
`nginx.conf` — раздаёт тот самый собранный бандл и проксирует `/api/*`
на backend с отрезанием префикса.

| Проверка | Результат |
|---|---|
| статика отдаётся | ✅ `GET /` → 200 |
| `GET /api/health` через прокси | ✅ 200, `model_loaded: true` |
| `GET /api/scenarios` | ✅ 200, шесть сценариев |
| `POST /api/scenarios/{key}/run` | ✅ 200 |
| бандл ходит на `/api`, а не на `localhost:8000` | ✅ проверено по содержимому бандла |
| интерфейс в браузере с origin `:3000` | ✅ статус модели и кнопки подтянулись |
| все шесть сценариев через продакшн-бандл | ✅ 0 / 35 / 55 / 73 / 100 / 60 |
| ошибки CORS в консоли | ✅ нет, запрос одноисточниковый |

Это проверяет главное: путь запроса, отрезание префикса, отсутствие CORS
и работоспособность собранного бандла. Не проверено то, что зависит от
самого Docker: корректность `Dockerfile` при реальной сборке, установка
`libgomp1`, работа healthcheck и `depends_on`.

**Что нужно сделать на машине с Docker:**

```bash
docker compose up --build
```

и убедиться, что открывается <http://localhost:3000>, а в логах backend
есть «Модель загружена».
