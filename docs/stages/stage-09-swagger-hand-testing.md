## Два принципа, без которых сценарии бесполезны

**Общий профиль клиента.** Все пять описывают одного и того же человека:
обычная сумма 100, дом — Казахстан, два известных устройства, три операции
в сутки, счёту 800 дней. Меняется ровно то, что заявлено в названии сценария.
Иначе сравнивать Risk Score между ними бессмысленно. Проверяется тестом
`test_scenarios_share_one_customer_profile`.

**Явный контекст и фиксированное время.** Профиль передаётся в каждом запросе
целиком, метки времени заданы абсолютными значениями. Поэтому результат не
зависит ни от накопленной истории, ни от часа запуска демонстрации.

Без этого свойства демонстрация выглядела бы как дефект: два нажатия —
два разных числа. Проверяется тестом `test_scenario_results_are_reproducible`.

Каждый сценарий дополнительно объявляет поле `changed_from_normal` — чем он
отличается от обычной транзакции. Тест сверяет, что заявленные поля
действительно отличаются: иначе описание сценария разошлось бы с его данными.

## Результат прогона

```
1. Normal transaction       0  APPROVE    LOW
2. New device              35  CHALLENGE  MEDIUM     ###########
3. Unusual country         55  CHALLENGE  MEDIUM     ##################
4. Large amount            73  BLOCK      HIGH       ########################
5. Multiple anomalies     100  BLOCK      CRITICAL   #################################
```

Пороги: `APPROVE <= 30 < CHALLENGE <= 70 < BLOCK`

| Проверка | Результат |
|---|---|
| рост монотонный от 1 к 5 | ✅ |
| сценарий 1 разрешён | ✅ |
| сценарии 2–4 выше базового | ✅ |
| сценарий 5 заблокирован | ✅ |

**Сценарий 4 обходится без политик** — крупную сумму распознаёт сама модель
(`model_score == risk_score == 73`, список правил пуст). Это важно показать
отдельно: иначе система выглядела бы набором правил, а не работающей моделью.
Зафиксировано тестом `test_scenario_4_is_caught_by_model_alone`.

Сценарии 2 и 3, наоборот, целиком заслуга политик: модель даёт 1 и 6 баллов,
а правила поднимают до 35 и 55. В документе это видно по строке
«Оценка модели без правил».

## Найденный дефект: я проверял устаревшую сборку

Открыв Swagger в браузере, я не увидел группы `scenarios` — были только
`system`, `prediction`, `transactions`. Выглядело так, будто роутер не
зарегистрировался, хотя `TestClient` минутой раньше показывал все восемь
маршрутов.

Причина оказалась не в коде. На этапе 08 сервер останавливался командой
`pkill -f "uvicorn app.main:app"`, и Git Bash отрапортовал об успехе — но
**Windows-процесс не умер**. Новый экземпляр не смог занять порт:

```
INFO:  Started server process [5392]
[Errno 10048] error while attempting to bind on address ('127.0.0.1', 8000)
INFO:  Остановка. Обработано транзакций: 0
```

Порт продолжал держать процесс 30868, запущенный в 15:11 — до того, как
сценарии вообще появились. Браузер показывал сборку получасовой давности.

Опасность здесь не в потерянных минутах, а в том, что дефект был бы
**ложноотрицательным в обратную сторону**: я мог зафиксировать в отчёте
несуществующую проблему или, хуже, пропустить настоящую. Правильный способ
остановки на Windows:

```powershell
Get-NetTCPConnection -LocalPort 8000 -State Listen |
  ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
```

Побочно подтвердилось, что правка UTF-8 из этапа 08 работает: лог нового
процесса читается по-русски.

## Почему документ генерируется, а не пишется руками

`docs/HAND_TESTING.md` собирается скриптом из фактических ответов системы.
Рукописная таблица разошлась бы с кодом после первого же переобучения модели
или правки порогов — и документация начала бы врать ровно там, где её будут
читать внимательнее всего.

Это тот же приём, что и с `docs/FEATURES.md` на этапе 05.

```bash
python backend/scripts/export_hand_testing.py
```
