# Shin — FinTech Anti-Fraud System

> **Shin** (каз. *шын* — «правда») — система выявления и предотвращения мошеннических
> транзакций в реальном времени: ML-скоринг, Risk Score 0–100, автоматическое решение
> и объяснение, почему это решение принято.

```
Transaction -> Feature Engineering -> ML Model -> Risk Score -> Risk Engine -> Decision -> XAI Explanation
```

## Демонстрация

| | |
|---|---|
| **Интерфейс** | **<https://shin-antifraud.onrender.com>** |
| API и Swagger | <https://shin-fraud-api.onrender.com/docs> |

> Backend развёрнут на бесплатном тарифе и засыпает после простоя. Первое
> обращение сначала будит контейнер — это до минуты, интерфейс в это время
> сам объясняет, что происходит. Дальше всё отвечает мгновенно.

## 1. Описание проекта

Shin принимает финансовую транзакцию, обогащает её поведенческими признаками
на основе профиля клиента, прогоняет через обученную ML-модель, переводит вероятность
фрода в **Risk Score (0–100)** и принимает одно из трёх решений:

| Decision | Risk Score | Что происходит |
|---|---|---|
| `APPROVE` | 0–30 | транзакция проходит |
| `CHALLENGE` | 31–70 | требуется 2FA / дополнительная проверка |
| `BLOCK` | 71–100 | транзакция блокируется |

Ключевое отличие от «чёрного ящика»: **каждое решение объясняется**. Система возвращает
3–5 главных факторов риска с величиной и направлением вклада каждого — это то, что
антифрод-аналитик может прочитать, а комплаенс — защитить перед регулятором.

Пороги решений конфигурируемые, и главное — **видно, во что обходится выбранная
конфигурация**. Дашборд показывает компромисс прямо: сколько фрода система ловит,
скольких добросовестных клиентов при этом задевает и как эти две величины меняются
при сдвиге порога чувствительности.

Интерфейс состоит из двух экранов:

| Экран | Что показывает |
|---|---|
| **Дашборд** | весь поток транзакций: пойманный и пропущенный фрод, трение, стоимость, вклад каждой политики, кривая Fraud Loss против Customer Inconvenience |
| **Симулятор** | одна операция вручную — Risk Score, решение и объяснение за секунду |

Аналитика по датасету считается заранее скриптом
`backend/scripts/export_evaluation.py` и отдаётся через `GET /analytics/overview`:
полный проход по 100 000 транзакций занимает около двадцати секунд, и ждать
столько в запросе нельзя. Ту же картину печатает в консоль
`backend/scripts/evaluate_risk_engine.py` — оба используют один расчёт
из `app/analytics/report.py`.

## 2. Архитектура

### 2.1 Поток обработки запроса

```
                            ┌──────────────────────────┐
  Test Web Interface ─POST /predict─►   FastAPI (api/routes)
  (React + Vite + TS)                 └────────────┬─────────────┘
        ▲                                          │ Pydantic-валидация
        │                                          ▼
        │                              PredictionService (services/)
        │                                          │  оркестрация
        │              ┌───────────────────────────┼───────────────────────────┐
        │              ▼                           ▼                           ▼
        │      UserProfileStore            FeatureBuilder                 ModelRegistry
        │      (история клиента)           (features/)                    (ml/loader)
        │              │                           │                           │
        │              └──────────► feature vector ┴──────► probability ◄──────┘
        │                                          │
        │                                          ▼
        │                                   RiskEngine (risk_engine/)
        │                                   score 0–100 + decision
        │                                          │
        │                                          ▼
        │                                   Explainer (xai/)
        │                                   вклады признаков + текст
        │                                          │
        └──────────────── JSON response ◄──────────┘
```

### 2.2 Слои и зона ответственности

| Слой | Каталог | Отвечает за | Не знает о |
|---|---|---|---|
| **API** | `backend/app/api/` | HTTP, валидация, коды ошибок | ML, бизнес-правилах |
| **Services** | `backend/app/services/` | оркестрация цепочки, работа с хранилищем | HTTP |
| **Features** | `backend/app/features/` | превращение транзакции в вектор признаков | FastAPI, ML-модели |
| **ML** | `backend/app/ml/` | датасет, обучение, загрузка модели, метрики | HTTP, Risk Score |
| **Risk Engine** | `backend/app/risk_engine/` | probability -> score -> decision, бизнес-правила | FastAPI |
| **XAI** | `backend/app/xai/` | вклады признаков и человекочитаемые причины | HTTP |
| **Config** | `backend/app/config/` | типизированные настройки из `.env` | всё остальное |

Принцип: **feature engineering живёт в одном модуле и используется и при обучении,
и при инференсе**. Это исключает training/serving skew — классическую причину, по которой
прототип показывает хорошие метрики на тесте и разваливается в проде.

### 2.3 Хранение данных

Реляционной СУБД в проекте нет, и это решение, а не пропуск. Ниже —
что именно хранится, где и что переживает перезапуск.

| Что | Где | Переживает перезапуск | Ёмкость |
|---|---|---|---|
| Метки аналитика | `backend/data/feedback/labels.jsonl` | **да** | без ограничения |
| Модель и её артефакты | `backend/models/` | **да** | 5 файлов |
| История операций | память, `TransactionStore` | нет | 5 000 последних |
| Профили клиентов | память, `UserProfileStore` | нет | по числу клиентов |
| Отпечатки повторов | память, LRU | нет | 5 000 |
| Наблюдения за дрейфом | память | нет | счётчики по корзинам |
| Правки конфигурации | память | нет | — |

Деление проходит по одной линии: **переживает перезапуск то, что нельзя
восстановить**. Метку аналитика заново не получить — за ней стоит работа
человека, разобравшего операцию. Модель заново не обучить без датасета,
которого в образе нет. Всё остальное система насчитывает сама из потока,
и после рестарта насчитает снова.

Хранилище меток устроено как журнал: строки дописываются в конец, при
чтении битые пропускаются и считаются. Приложение, не поднявшееся из-за
одной недописанной строки, хуже приложения с неполной разметкой.
На бесплатном хостинге файловая система бывает недоступна для записи —
тогда метка остаётся в памяти и работает, а причина уходит в сводку,
чтобы пропажа архива не осталась незамеченной.

**Почему не PostgreSQL.** Для демонстрации СУБД добавила бы контейнер,
миграции, пул соединений и ещё один способ не запуститься — не добавив
ни одной возможности, которой нет сейчас. Требование §7 «Бэкенд и База
данных» закрыто REST-эндпоинтом и этим слоем хранения; минимальное
ожидание — работающий `POST /predict` — выполнено с запасом.

**Что изменится в проде.** Профили и история переедут в БД первыми: они
растут линейно с числом клиентов, а память контейнера — нет. Слой
хранилищ (`backend/app/store/`, четыре класса) для этого и отделён от
сервисов: переезд меняет два из них, а цепочку обработки — ни одним
местом. См. «Возможные улучшения».

## 3. Технологический стек

### 3.1 Backend

| Технология | Версия | Роль в проекте |
|---|---|---|
| **Python** | 3.11+ (проверено на 3.14) | язык backend |
| **FastAPI** | >=0.115 | REST API, автоматический OpenAPI/Swagger |
| **Uvicorn** | >=0.30 | ASGI-сервер |
| **Pydantic** | v2 | схемы запросов/ответов, валидация, type safety |
| **pydantic-settings** | >=2.4 | конфигурация из `.env` с типами |
| **python-dotenv** | >=1.0 | загрузка переменных окружения |

### 3.2 Data & Machine Learning

| Технология | Роль |
|---|---|
| **NumPy** | векторные вычисления, генерация датасета |
| **pandas** | работа с табличными данными, CSV |
| **scikit-learn** | препроцессинг, split, метрики, baseline-модели |
| **joblib** | сериализация обученной модели |
| **LightGBM** | основной градиентный бустинг (установлен: 4.7.0) |

**Стратегия выбора модели** (см. [D-2](docs/TZ.md#отклонения-и-решения)):

```
LightGBM  ->  (если недоступен)  sklearn HistGradientBoostingClassifier
```

`GradientBoostingClassifier` доступен третьим вариантом по явному флагу
`--algorithm gradient_boosting`. Система всегда обучает **настоящую** модель —
никаких случайных заглушек, это проверяется тестом `test_model_is_not_a_random_stub`.

### 3.3 Explainable AI

| Технология | Роль |
|---|---|
| **SHAP** | точные значения Шепли через `TreeExplainer` (установлен: 0.52.0) |
| **LightGBM `pred_contrib`** | те же значения Шепли без внешнего пакета — объяснения остаются точными в минимальной установке |
| **Ablation** | замена признака на эталон из данных; работает с любой моделью и объясняет итоговую вероятность |
| **Narrator** | перевод технического признака в формулировку для человека |

### 3.4 Frontend

Минимальный тестовый интерфейс: одна страница, без роутинга и графиков.

| Технология | Роль |
|---|---|
| **React 18** | UI |
| **TypeScript** | типы, зеркалящие Pydantic-схемы |
| **Vite 5** | dev-сервер и сборка |
| **обычный CSS** | без UI-фреймворков |
| **fetch** | запросы к `POST /predict` |

Frontend делает ровно одно: `Input -> POST /predict -> Display Response`.
Дублировать Risk Engine, пороги или расчёт признаков на клиенте запрещено —
такая копия разойдётся с backend и начнёт показывать не то, что система
решила на самом деле.

### 3.5 Инфраструктура и качество

| Технология | Роль |
|---|---|
| **Docker + docker compose** | запуск всего проекта одной командой |
| **Nginx** | раздача собранного frontend в контейнере |
| **pytest + httpx** | тесты API и сценариев hand-testing |

### 3.6 Что сознательно НЕ используется

| Отказались | Почему |
|---|---|
| PostgreSQL / Redis | БД добавила бы контейнер, миграции и ещё один способ не запуститься, не добавив возможностей; что и где хранится — в разделе 2.3 |
| Kafka / очереди | прототип синхронный: «ввёл транзакцию — увидел решение» |
| Auth / JWT | демо-стенд без чувствительных данных; см. «Возможные улучшения» |
| Tailwind / MUI | интерфейс — одна страница; нужен читаемый студенту CSS |

## 6. Запуск ML training

Генерация синтетического датасета на 100 000 транзакций:

```bash
python backend/scripts/generate_dataset.py --rows 100000 --seed 42
```

Обучение модели и сохранение артефакта:

```bash
python backend/scripts/train_model.py
```

Обе команды печатают отчёт и завершаются с ненулевым кодом, если результат
непригоден: генератор — при провале валидации данных, обучение — если
сохранённая модель предсказывает иначе, чем обученная, или если ROC-AUC
ниже 0.7.

Полезные флаги обучения:

```bash
python backend/scripts/train_model.py --algorithm hist_gradient_boosting --calibration isotonic
```

Проверить окружение и наличие артефактов:

```bash
python backend/scripts/check_setup.py
```

*Разделы 7–12 и 15 README дополняются фактическими командами и примерами
ответов по мере закрытия этапов — см. [docs/STAGES.md](docs/STAGES.md).
Все числа в документации — настоящие ответы системы, а не плановые.*

### Дашборд

Открывается первым. Показывает работу системы на всём датасете: пойманный
и пропущенный фрод, долю задетых добросовестных клиентов (False Positive Rate),
разбивку решений, вклад каждой политики и кривую компромисса с ползунком порога.

Дашборду нужен выгруженный отчёт. Если его нет, экран честно скажет об этом
и назовёт команду:

```bash
python backend/scripts/export_evaluation.py
```

Ползунок порога не меняет настройки системы — он показывает, что было бы при
другом пороге на тех же данных. Все точки кривой посчитаны заранее.

### Симулятор: что можно проверить за 10 секунд

1. открыть <http://localhost:5173>;
2. нажать кнопку сценария — форма заполнится;
3. поменять `amount`, `country`, `device_id`, `transaction_frequency`;
4. нажать **Analyze Transaction**;
5. увидеть новый Risk Score, Decision и объяснение.

Кнопки-пресетов шесть, и они берутся с `GET /scenarios` — тот же источник,
что у автотестов и [docs/HAND_TESTING.md](docs/HAND_TESTING.md), поэтому
разойтись с ними не могут.

### Признаки видно, а не только пять сильнейших

Система считает из транзакции 27 величин, и кейс называет две из них
поимённо: «расчет отклонений от среднего чека, скорости перемещения
между IP» (§5.B). Считались они с самого начала, но увидеть их было
негде: таблица вкладов показывает пять сильнейших, остальные лежали
в сыром JSON под спойлером.

Панель «Признаки операции» под вердиктом показывает весь вектор
с описаниями, разбитый по пунктам ТЗ §4. Названные в кейсе величины
выделены.

Описания приходят из `GET /features` — одним запросом на сессию.
Держать их копию в интерфейсе значило бы завести второй список
признаков, который однажды разойдётся с реестром модели.

```bash
curl "http://localhost:8000/features"
```

### Обратная связь аналитика: откуда в системе берётся правда

Под вердиктом стоят две кнопки — **Вердикт верный** и **Вердикт ошибочный**.
Это не оценка интерфейса, а единственный канал, по которому в работающую
систему попадает истина.

Без неё все метрики в проде — самооценка: `GET /stats` считает долю
рискованных по собственным вердиктам и честно оговаривает, что измеренной
истиной это не является. Разметка аналитика превращает оговорку в число:
панель «Разметка аналитика» на дашборде показывает подтверждённую точность,
ложные срабатывания и пропущенный фрод — по тем операциям, которые разобрал
человек.

Спрашивать «это был фрод?» напрямую не нужно: система знает, что утверждала,
и выводит метку сама. Подтверждённый BLOCK означает фрод, подтверждённый
APPROVE — чистую операцию.

Накопленное — датасет, а не журнал кликов. Метка хранит слепок решения
(Risk Score, вердикт, сработавшие политики), потому что буфер транзакций
ограничен и к моменту дообучения самой операции в памяти уже не будет.
Метки дописываются в `backend/data/feedback/labels.jsonl` построчно: это
единственное в системе, что нельзя пересчитать заново.

```bash
curl -X POST "http://localhost:8000/transactions/txn_001/feedback" \
  -H "Content-Type: application/json" \
  -d '{"verdict": "INCORRECT", "analyst": "ops", "comment": "клиент подтвердил покупку"}'
```

Забрать накопленное целиком — `GET /feedback`. На хостинге с эфемерным
диском это единственный способ достать разметку до того, как контейнер
погаснет.

### Партия и поток: когда операций много

Кейс §4.1 говорит, что система принимает транзакцию «в режиме реального
времени через API **или батч-обработкой**», а §5.B требует «интерфейс или
API для загрузки синтетического датасета (100k строк) **или симуляции
потока транзакций**». Отсюда два эндпоинта, и они отвечают на разные
вопросы.

`POST /predict/batch` — «оцени вот эти операции». До двухсот штук за раз,
вердикт по каждой, порядок ответа совпадает с порядком запроса. Партия
наследует идемпотентность одиночного `/predict`: повторно отправленная,
она не удвоит ни историю, ни профили клиентов, и сколько операций
обслужено повтором, видно в поле `replayed`.

`POST /predict/stream` — «сделай поток и прогони его». Это нужно потому,
что наблюдение за дрейфом, теневая конфигурация и история операций
показывают что-либо **только на потоке**: на свежем экземпляре системы
они пусты, и понять, работают ли панели, нельзя. Дрейфу вдобавок нужно
не меньше двухсот наблюдений, прежде чем он назовёт хоть одно число.
На дашборде для этого есть кнопки «Прогнать 100 / 300 / 500».

Разметка потока известна — операции порождены тем же генератором, на
котором обучалась модель, — поэтому сводка показывает не только
распределение решений, но и сколько фрода поймано и сколько пропущено.
Это проверка на живых данных, а не число из выгруженного артефакта.

```bash
curl -X POST "http://localhost:8000/predict/stream" -H "Content-Type: application/json" -d '{"count": 300}'
```

**Поток берётся выборкой из порождённого датасета, а не генерируется
нужного размера.** Сначала было наоборот, и это оказалось неверно —
показало само наблюдение за дрейфом. Статистики генератора зависят от
объёма: в выборке на триста строк у клиента две-три операции вместо
тридцати, и `transaction_frequency` расходится с обучающим
распределением (PSI до 5.4). Сделать клиентов мало, чтобы история
набралась, тоже нельзя — тогда вырождается `account_age_days`: он
постоянен внутри клиента, и триста операций дают девять значений вместо
гладкого распределения (PSI 3.2). Оба конца показывали дрейф, которого
на самом деле нет.

Теперь порождается полноценный датасет на десять тысяч строк с тем же
соотношением операций на клиента, что в обучающем (33:1), и выборка
берётся из него: дрейф на таком потоке — «стабильно», ноль признаков за
границей, худший PSI 0.05. Пул строится один раз на процесс, это около
секунды и восьми мегабайт.

### Карта аномалий

Бонус брифинга §6: «Интерактивная карта аномалий: визуализация
геолокаций подозрительных попыток входа/платежей».

Размер кружка — объём операций, цвет — доля мошеннических среди них,
пунктирное кольцо — страна из списка повышенного риска. Наведение
показывает точные числа: на карте видно, **где** смотреть, а не сколько
именно.

Картина получается говорящая. Казахстан — база: 58 521 операция при
доле фрода 1 %. И хвост из десятка стран, где мошеннической оказывается
почти каждая операция: Венесуэла, Индия, Бразилия, США — по полусотне
операций и 100 % фрода. Это адресаты атак, а не источники трафика.

**Без картографической библиотеки и без подложки.** Leaflet притащил бы
зависимость и запросы к чужому серверу тайлов — карта переставала бы
рисоваться без интернета и подглядывала бы за тем, кто её открыл.
А рисовать материки от руки значило бы поставить береговые линии
наугад: карта, где Каспий не на месте, хуже честной сетки координат.
Вместо подложки — градусная сетка с подписями: проекция видна,
положение точки проверяемо.

Координаты берутся из того же справочника, по которому считается
скорость перемещения между операциями (`features/geo.py`). Второй набор
координат ради карты разошёлся бы с первым, и карта показывала бы не то
место, где система увидела аномалию.

### Три языка: русский, казахский, английский

Бонус брифинга §6 и рабочие языки хакатона (Положение §1.6). Переключатель
в шапке, выбор запоминается.

**Переведена продуктовая поверхность** — заголовки, кнопки, подписи
плиток, названия решений и уровней риска, столбцы таблиц, названия
демонстрационных сценариев. Это то, чем человек пользуется.

**Переведено и то, что приходит с backend**: описания признаков,
пояснения к решениям, описания сценариев, текстовый отчёт `/report`.
Держать их перевод на клиенте было нельзя — по ТЗ §11 интерфейс ничего
не вычисляет сам, а вторая копия формулировок однажды разошлась бы
с первой. Поэтому язык — параметр запроса: `?language=ru|kk|en`.

**Не переводится намеренно** и проверяется тестами: технические имена
признаков (по ним число вектора соединяется с описанием), ключи
сценариев и политик, коды стран в таблицах, названия мерчантов
и формулировки причин из XAI — последние ТЗ §7 задаёт по-английски.

**Подробные пояснения к панелям остались русскими.** Их 55 блоков
примерно на полторы тысячи слов, и написаны они как объяснение читателю,
а не как текст продукта. В казахском и английском режимах они убираются
и возвращаются переключателем над дашбордом.

Причина названа прямо, а не спрятана: полторы тысячи слов машинного
казахского на жюри, у которого казахский рабочий, — хуже, чем русский
комментарий, о котором сказано, что он русский. Реализовано одним
правилом CSS по `data-lang` на корне, а не полусотней правок
по компонентам.

**Текст клиенту пишется на его языке.** Это не про кнопки: банк пишет
человеку на понятном ему языке, и письмо про приостановленную операцию —
ровно тот случай. Языковая модель получает язык в системном промпте
и пишет сама; запасной текст переведён руками, потому что обязан
работать без неё.

```bash
curl -X POST "http://localhost:8000/explain/client?language=kk" -H "Content-Type: application/json" -d @transaction.json
```

Проверка на противоречие вердикту работает на всех трёх языках сразу:
модель, которую попросили писать по-казахски, может ответить по-русски,
и «операция отклонена» вместо «подтвердите» должно ловиться в обоих
случаях.

> **Казахские формулировки писал не носитель языка.** Их десяток, и
> перед сдачей их стоит прочитать человеку, для которого казахский
> родной. Сказано прямо, потому что молча выдать машинный перевод
> за готовый текст — хуже, чем признать ограничение.

### Что сказать клиенту: LLM-ассистент

Бонус брифинга §6: «LLM-Ассистент Риск-аналитика: генерация естественного
ответа для клиента, объясняющего, почему потребовалось 2FA-подтверждение».

**Языковая модель здесь не решает — она формулирует.** Вероятность даёт
LightGBM, оценку и вердикт — Risk Engine, причины — SHAP. Ассистент
получает готовые факты и превращает их во фразу, которую можно отправить
человеку. Выключите его — система работает так же, изменится только текст.

Три вещи делают это проверяемым, а не декларацией:

| | |
|---|---|
| Ответ сверяется с вердиктом | текст со словами противоположного решения не показывается: для клиента «отклонена» и «подтвердите» — разные новости |
| Видно, кто написал | поле `source` равно `llm` или `fallback`; выдавать шаблон за работу ассистента нельзя |
| Видно, что уходит наружу | поле `facts` — ровно тот блок, что отправляется провайдеру: без идентификатора клиента, номера операции и IP |

**Без ключа система работает.** Текст тогда собирается из тех же фактов
детерминированно, и в ответе честно стоит `source: fallback`. Ключ
хранится `SecretStr`, не появляется ни в логе, ни в трассировке, ни
в сообщении об ошибке — тело ответа провайдера наружу не уходит,
потому что может содержать эхо запроса вместе с заголовком авторизации.

```bash
curl -X POST "http://localhost:8000/explain/client" -H "Content-Type: application/json" -d @transaction.json
```

Провайдер задаётся двумя переменными (`LLM_BASE_URL`, `LLM_MODEL`):
формат chat completions одинаков у DeepSeek, OpenAI и большинства
остальных.

### Адаптивный порог: чувствительность своя у каждой категории

Бонус брифинга §6: «автоматическая подстройка чувствительности модели
в зависимости от времени суток или категории мерчанта».

Ни один порог не назначен руками. Для каждой категории мерчанта берётся
минимум той же функции стоимости, по которой построена кривая
компромисса, — те же веса, та же формула. Назначить сдвиги вручную было
бы быстрее и бессмысленно: это третий слой захардкоженных чисел поверх
модели, и **интуиция здесь ошибается знаком**. Кажется, что у криптобирж
и обменников порог надо опускать, раз через них выводят украденное.
Подобранный оказывается выше общего: модель уже учитывает категорию
признаком `is_high_risk_merchant`, и низкий порог поверх этого просто
заваливает проверками честные операции.

Разброс подобранных порогов — от 3 у транспорта до 61 у электроники при
общем 4. На практике это значит, что одна и та же оценка решается
по-разному:

| Мерчант | Категория | Risk Score | Порог | Решение |
|---|---|---|---|---|
| Magnum | grocery | 12 | 11 | CHALLENGE |
| Technodom | electronics | 12 | 61 | APPROVE |

**Чего это стоит.** Проверка перекрёстная на пяти частях: порог сегмента
подбирается без тех операций, на которых потом считается результат.

| | |
|---|---|
| Выигрыш против одного подобранного порога | +614 в среднем, **худшая часть −900**, положительных 4 из 5 |
| Против действующей настройки | стоимость −1 078, трение **−716** (2 011 → 1 295), пойманного фрода −14 |

Главный эффект — на треть меньше побеспокоенных честных клиентов,
и он куплен четырнадцатью пропущенными операциями. Выигрыш невелик
и не гарантирован: в одной части из пяти режим проиграл, и панель
показывает это наравне с остальным.

**Время суток проверялось тоже и в среднем проигрывает** (−139 при
худшей части −2 463), поэтому не применяется. Брифинг говорит «времени
суток **или** категории мерчанта», так что одной категории достаточно.

Режим выключен по умолчанию: выгруженная аналитика считается на одном
пороге для всех операций, и включённый режим разошёлся бы с числами на
дашборде. Панель показывает измеренный эффект и выключенного режима —
решать вслепую не нужно.

```bash
curl "http://localhost:8000/config/adaptive"
```

### Дрейф данных: поломка, которую больше нечем заметить

Модель обучена на сгенерированном датасете и с тех пор не менялась. Когда
живой поток перестаёт походить на обучающий, её оценки становятся
недостоверными — и **система об этом не сообщит**. Исключения нет, в логах
пусто, `/health` зелёный, ответ по-прежнему число от 0 до 100. Просто это
число уже ни о чём не говорит.

Ни тест, ни healthcheck такого не ловят. Ловит только сравнение
распределений, и панель «Сдвиг распределения» на дашборде показывает его
по каждому из 27 признаков.

Мера — Population Stability Index, привычный в скоринге: до 0.1 стабильно,
0.1–0.25 умеренный сдвиг, дальше существенный. Выбран он не только за
привычность. PSI считается по корзинам, то есть **не требует хранить
наблюдения**: в памяти живут три сотни счётчиков независимо от того,
миллион транзакций прошёл или три. Наблюдение ничего не знает о клиентах
и не растёт со временем.

Эталон снимается тем же проходом по датасету, что и аналитика
(`export_evaluation.py` пишет оба артефакта), а счётчики живут до
перезапуска: в отличие от разметки аналитика, их восстанавливает
обычный трафик.

```bash
curl "http://localhost:8000/monitoring/drift"
```

Пока наблюдений меньше двухсот, числа не называются — на полусотне
транзакций PSI меряет случайность. Режим «что если» (`persist=false`)
в наблюдение не попадает: десяток нажатий Analyze на одном сценарии
сдвинул бы картину сильнее, чем настоящий поток.

### Теневая конфигурация: проверить гипотезу, не трогая систему

Дашборд говорит неприятное: текущий порог 30 далеко от самого дешёвого
(4), а четыре политики из шести не ловят ничего сверх модели и приносят
одно трение. Но по этим числам никто не станет переключать работающую
систему, и правильно не станет — кривая отвечает, что было бы **на
обучающем датасете**.

Теневой режим отвечает на другой вопрос: что происходит **на сегодняшнем
потоке**. Вторая конфигурация видит те же настоящие операции и выносит
свои решения — и они никуда не уходят. Ответ `POST /predict` от них
не зависит ни одним полем, в историю и профиль клиента они не попадают,
деньги по ним не блокируются.

Это главное свойство, и оно закреплено тестом, который сравнивает ответ
с включённой тенью и с выключенной целиком, до последнего поля.

Панель «Теневая конфигурация» показывает матрицу «кто что решил»,
разделяет расхождения на снятое и добавленное трение и приводит
последние операции, по которым конфигурации разошлись.

```bash
curl "http://localhost:8000/monitoring/shadow"
```

Настраивается переменными `SHADOW_*`. По умолчанию тень проверяет ровно
то неприятное открытие: те же пороги, но без политик. На живом потоке
из 120 операций это дало 97.5 % совпадений и три операции, которые
политики отправили на проверку, а модель считала чистыми.

### Связи между клиентами: то, чего не видно по одной операции

Признаки описывают одну транзакцию, модель оценивает одну, политики
проверяют одну. Кольцо так не видно **в принципе**: десять «разных»
клиентов, заходящих с одного устройства, поодиночке безупречны — сумма
обычная, страна привычная, устройство для каждого из них своё привычное.

Панель «Связи между клиентами» строит граф: клиенты, их устройства
и подсети /24. Группы, где клиентов больше одного, — кандидаты в кольца.

**Связи не равнозначны, и они не смешиваются в одно число.** Один
физический телефон у трёх «разных» людей объясняется плохо. А общую
подсеть делят корпоративный NAT, оператор мобильной связи и один
провайдер в одном доме — такие группы помечены отдельно и сами по себе
почти ничего не значат. Сводной «оценки подозрительности» здесь нет:
её пришлось бы придумать, а вес взять с потолка.

**Граф строится по живому потоку, а не по датасету.** В сгенерированных
данных колец нет по построению: идентификаторы устройств собираются как
`dev_{номер клиента}_{n}`, то есть пространство имён разделено
по клиентам и пересечься не может. Из 8 414 устройств датасета
у более чем одного клиента ровно одно, общих подсетей — ноль. Кольца
и положено искать по недавней активности.

Проверяется за три операции: отправьте в симуляторе несколько запросов
от разных `user_id` с одним `device_id`.

```bash
curl "http://localhost:8000/graph/clusters"
```

Граф ничего не меняет в решениях — это анализ, а не политика.

### Отчёт по операции текстом

`POST /predict` отдаёт всё, что система знает о решении, и интерфейс
раскладывает это по панелям. Но обе формы предполагают, что читатель
сидит перед Shin.

Аналитик живёт не там. Он пишет в тикет, отвечает клиентской службе,
прикладывает обоснование к решению по обращению. Вставить туда JSON
нельзя, а пересказывать своими словами — значит каждый раз заново
придумывать формулировки и однажды написать не то, что система решила
на самом деле.

Кнопка **«Показать отчёт»** под вердиктом в симуляторе — и то же самое
через API:

```bash
curl -X POST "http://localhost:8000/report" \
  -H "Content-Type: application/json" \
  -d @transaction.json
```

Ответ — `text/plain`: одна страница с решением, причинами, сработавшими
политиками, таблицей вкладов и пометкой, какой моделью это посчитано.
Последнее важно: через месяц модель будет другой, и без метки непонятно,
на чём основано решение.

**Отчёт ничего не меняет.** Поле `persist` игнорируется: составление
отчёта — чтение, а не обработка. Иначе аналитик, перечитавший
обоснование трижды, трижды добавил бы операцию в статистику.

Формулировки причин остаются английскими — их задаёт ТЗ §7, и это
официальная формулировка системы. Перевод здесь завёл бы вторую версию
того же утверждения: в API одна, в отчёте другая, и при расхождении
не понять, какая настоящая.

### Повторы безопасны

Повтор запроса — обычное дело: клиент не дождался ответа и переспросил,
прокси повторил за него, пользователь нажал кнопку дважды.

Без идемпотентности каждый повтор обрабатывался заново, и последствий
было четыре. Операция дважды попадала в историю и в `/stats`. Дважды
учитывалась наблюдением за дрейфом и теневым сравнением. Профиль клиента
обновлялся дважды.

И самое неприятное: **второй ответ мог отличаться от первого**. Именно
потому, что профиль уже обновлён первым вызовом — устройство, которое
было новым, новым быть переставало. Клиент переспросил из-за таймаута
и получил другой вердикт по той же операции.

Теперь `POST /predict` идемпотентен по `transaction_id`:

| Ситуация | Ответ |
|---|---|
| Тот же номер, то же тело | прежний ответ, заголовок `Idempotent-Replay: true`, состояние не тронуто |
| Тот же номер, **другое** тело | `409` — это вторая операция под чужим номером |
| Режим «что если» (`persist=false`) | не кэшируется вовсе |

Последнее намеренно: `persist=false` существует ровно для того, чтобы
гонять один и тот же ввод сколько угодно раз.

Поэтому симулятор обновляет `transaction_id` после каждого анализа —
следующий прогон это новая операция, а не переписанная старая.

Выключается `IDEMPOTENCY_ENABLED=false`.

### Пороги меняются без перезапуска

Дашборд показывает, что самый дешёвый порог — 4, а работает 30. Теневой
режим показывает, что дало бы переключение на сегодняшнем потоке. После
этого предлагать «поправьте `.env` и перезапустите прод» было бы
издевательством.

```bash
curl -X POST "http://localhost:8000/config/thresholds" \
  -H "Content-Type: application/json" \
  -H "X-Admin-Token: $CONFIG_ADMIN_TOKEN" \
  -d '{"approve_max": 4, "challenge_max": 70, "critical_min": 90,
       "rules_enabled": false, "changed_by": "ops", "reason": "дно кривой"}'
```

Смена порога — не присваивание. От порогов зависит всё, что система уже
насчитала, поэтому за ними приводится остальное:

| Что | Что с ним делается | Почему |
|---|---|---|
| Теневое сравнение | обнуляется и пересобирается | сравнивает две конфигурации; если одна изменилась посреди набора, матрица смешивает разное |
| Аналитика дашборда | помечается устаревшей | посчитана на прежних порогах |
| Наблюдение за дрейфом | **не трогается** | сравнивает распределение признаков, а пороги на признаки не влияют |
| История операций | сохраняется, `/stats` сообщает время смены | в ней операции, которые аналитику ещё размечать, и по ней строится граф связей |

**Перезапуск всегда возвращает к `.env`.** Правки живут только в памяти,
поэтому неудачную отменяет рестарт, а не поиск того, кто её сделал.

**Запись закрыта паролем и выключена, пока он не задан.** Адресом,
которым ставится `approve_max = 100`, отключается блокировка любого
мошенничества, а публичный стенд у проекта есть. Общий пароль — не
аутентификация: он не различает людей и не отзывается по одному.
Настоящей системе нужны учётные записи и журнал действий; здесь закрыта
дыра, а не решена задача доступа.

Интерфейс менять пороги не умеет намеренно: это действие оператора,
а не кнопка в браузере — иначе пароль пришлось бы положить в клиент.
Показывает он их правильно и без правок: и симулятор, и баннер
устаревшей аналитики читают действующие значения из ответов API.

### Веса рисков и бизнес-метрика — тоже без перезапуска

Брифинг §4.5 требует возможности «корректировать веса рисков»,
§5.C — «гибкую настраиваемую бизнес-метрику». Оба адреса устроены как
пороги: читать открыто, писать по паролю, перезапуск возвращает к `.env`.

**Политики** — с какой оценки каждая поднимает риск:

```bash
curl -X POST "http://localhost:8000/config/policies"   -H "Content-Type: application/json"   -H "X-Admin-Token: $CONFIG_ADMIN_TOKEN"   -d '{"new_device_min_score": 85, "changed_by": "ops",
       "reason": "много захватов аккаунтов"}'
```

Незаданные политики остаются как есть. Последствия те же, что у смены
порогов, и по тем же причинам: политики решают судьбу операции наравне
с моделью.

**Бизнес-метрика** — во что система оценивает свои ошибки:

```bash
curl -X POST "http://localhost:8000/config/cost"   -H "Content-Type: application/json"   -H "X-Admin-Token: $CONFIG_ADMIN_TOKEN"   -d '{"false_challenge": 120, "changed_by": "риск-аналитик"}'
```

Здесь последствие другое и главное: **кривая компромисса
пересчитывается на месте**, и дашборд сразу показывает новый оптимум.
Сказать «лишняя проверка стоит 120, а не 12» значит сказать системе
«беспокоить клиента дорого» — и самый дешёвый порог уезжает с 4 на 60.

Пересчёт не требует датасета: в каждой точке кривой лежат счётчики
и сумма пропущенного фрода, а веса лишь превращают их в деньги. Это
важно, потому что в проде датасета и нет — образ удаляет его после
обучения.

Аналитика при этом **не** помечается устаревшей: её числа посчитаны
только что. Отчёт, выгруженный старой версией и сумм не хранящий,
пересчитать нечем — тогда ответ честно говорит `curve_recomputed: false`.

Веса не влияют на решения: они переводят уже принятые решения в деньги.
Проверяется тестом — иначе настройка отчётности однажды начала бы
двигать вердикты.

Метрика видна на дашборде под кривой, без пароля: иначе деньги
на графике появлялись бы ниоткуда.

### Как устроена сеть

Браузер работает на машине пользователя и внутреннюю сеть Docker не видит:
адрес вроде `http://backend:8000` оттуда не резолвится. Поэтому интерфейс
собран с `VITE_API_URL=/api` и шлёт запросы на **тот же origin**, а nginx
переправляет их в контейнер backend:

```
браузер ──/api/predict──► nginx (frontend:80) ──/predict──► backend:8000
```

Завершающий слэш в `proxy_pass http://shin_backend/;` отрезает префикс `/api`.
Побочная выгода: запросы становятся одноисточниковыми, и CORS в этой схеме
не участвует вовсе.

## 13. Описание ML-модели

| Параметр | Значение |
|---|---|
| Алгоритм | LightGBM 4.7.0 (`LGBMClassifier`, 400 деревьев, learning rate 0.05) |
| Fallback | sklearn `HistGradientBoosting`, если LightGBM недоступен |
| Признаков | 28 — см. [docs/FEATURES.md](docs/FEATURES.md) |
| Обучающая выборка | 99 360 транзакций, доля фрода 1.95 % |
| Разбиение | train / calibration / test = 60 / 20 / 20, стратифицированно |
| Дисбаланс классов | вес положительного класса = √(neg/pos) ≈ 7.1 |
| Калибровка вероятностей | sigmoid (Платт) на отдельной части выборки |
| Время обучения | ~11 с |

### Метрики на тестовой выборке (19 872 транзакции)

| Метрика | Значение |
|---|---|
| ROC-AUC | **0.9936** |
| PR-AUC | **0.919** |
| Precision (порог 0.50) | **0.9517** |
| Recall (порог 0.50) | **0.8225** |
| F1 (порог 0.50) | **0.8824** |
| Brier score | 0.003811 |
| TP / FP / FN / TN | 317 / 22 / 70 / 19 463 |

Лучший F1 достигается на пороге 0.6: **0.8748**
(precision 0.9599  recall 0.8036). Рабочий порог системы —
0.31  граница `APPROVE`/`CHALLENGE`  а не 0.50  поэтому практический recall
ближе к значению из этой строки.

PR-AUC указан рядом с ROC-AUC намеренно: при доле фрода около 2 % именно он
честно показывает качество, тогда как ROC-AUC на сильном дисбалансе всегда
выглядит близким к единице.

Актуальные метрики всегда лежат в `backend/models/model_metrics.json` —
файл перезаписывается при каждом обучении.

### Почему вероятности калибруются

Risk Score считается как `probability × 100`, поэтому вероятность обязана быть
настоящей вероятностью. Взвешивание редкого класса систематически завышает
её, а калибровка на отложенной выборке возвращает физический смысл: среди
транзакций с Risk Score около 65 действительно около 65 % мошеннических.

Метод — **sigmoid**, а не isotonic: изотоническая регрессия на этой задаче
вырождается в ступеньку и выдаёт почти только 0 или 100, из-за чего полоса
`CHALLENGE` становится недостижимой. Подробности — в
[отчёте этапов 03–04](docs/stages/stage-03-04-ml-pipeline.md).

## 14. Описание Risk Score

`Risk Score = round(probability * 100)`, где `probability` — вероятность фрода от модели,
скорректированная жёсткими бизнес-правилами Risk Engine.

| Risk Score | Risk Level | Decision |
|---|---|---|
| 0–30 | `LOW` | `APPROVE` |
| 31–70 | `MEDIUM` | `CHALLENGE` |
| 71–100 | `HIGH` | `BLOCK` |

Границы задаются в `.env` (`RISK_APPROVE_MAX`, `RISK_CHALLENGE_MAX`).
`RiskEngine` принимает пороги объектом, поэтому один и тот же поток можно
пересчитать при разных границах без перезапуска — этим пользуется
`backend/scripts/evaluate_risk_engine.py`.

### Слой бизнес-правил

Поверх модели работают жёсткие политики. Каждая задаёт **минимальный** Risk
Score при срабатывании: правила только поднимают оценку и никогда не снижают.

| Политика | Условие | Мин. балл |
|---|---|---|
| `impossible_travel` | перемещение физически недостижимо за прошедшее время | 75 |
| `velocity_burst` | ≥ 6 операций за час | 60 |
| `new_account_large_amount` | новый счёт **и** сумма ≥ 4× обычной | 60 |
| `high_risk_country` | страна из списка повышенного риска | 55 |
| `unusual_country` | чужая страна **и** (новое устройство **или** новая сеть) | 40 |
| `new_device` | новое устройство **и** новая сеть | 35 |

Условия составные намеренно. Одиночные («любая чужая страна», «любое новое
устройство») отправляли на проверку 10.2 % добросовестных клиентов, почти не
добавляя пойманного фрода — модель ловила его и без них. Составные условия
снизили трение до 2.0 %. Измерения — в
[отчёте этапа 06](docs/stages/stage-06-risk-engine.md).

Ответ API содержит и `model_score` (чистый выход модели), и `risk_score`
(после правил), поэтому всегда видно, что подняло риск:

```
Scenario            ML   итог   решение     политика
New device           1     35   CHALLENGE   new_device
Large amount        73     73   BLOCK       — (сработала только модель)
```

Проверить конфигурацию на реальном потоке:

```bash
python backend/scripts/evaluate_risk_engine.py
```

Отключить правила целиком и увидеть чистый ML: `RULES_ENABLED=false` в `.env`
или флаг `--no-rules` у скрипта.

## 15. Описание XAI

Объяснение собирает **два независимых источника**: вклады признаков модели
и сработавшие политики Risk Engine. Показывать только первое было бы неполно:
в сценарии «новое устройство» модель даёт 1 балл, а итоговые 35 — целиком
заслуга правила.

### Движки вкладов

| Движок | Что считает | Когда используется |
|---|---|---|
| `shap` | точные значения Шепли (`shap.TreeExplainer`) | установлен пакет `shap` |
| `lightgbm_native` | те же значения Шепли, встроенные в LightGBM | `shap` не установлен |
| `ablation` | изменение вероятности при замене признака на эталон | любая модель |

Средний вариант важен: LightGBM считает TreeSHAP сам, поэтому объяснения
остаются **точными** даже без пакета `shap`, а не деградируют до приближения.
Числа обоих движков совпадают до `1e-6` — это проверяется тестом.

SHAP и встроенный расчёт объясняют логит базовой модели до калибровки;
калибровка монотонна, поэтому порядок и знак вкладов сохраняются. Единицы
измерения возвращаются в поле `units`, чтобы это не приходилось угадывать.

### Пример вывода

```
3 Unusual country   Risk Score: 55   Decision: CHALLENGE   (MEDIUM)
  Reasons:
    - Transaction from a high-risk country
    - Transaction from an unusual country on an unfamiliar connection
    - Implied travel speed of 396 km/h between transactions
    - Unusual country: transaction outside the user's home country
    - Transaction 7922 km away from the previous one
  Feature contributions (logit):
    travel_speed_kmh      = 396   +2.6998  INCREASES_RISK
    is_unusual_country    = yes   +1.0957  INCREASES_RISK
    is_high_risk_country  = yes   +0.8406  INCREASES_RISK
    geo_distance_km       = 7922  +0.7645  INCREASES_RISK
    hours_since_previous  = 20.00 -0.7203  DECREASES_RISK
```

Последняя строка показательна: «прошло 20 часов» **понижает** риск — за такое
время долететь можно. Объяснение показывает не только обвинение, но и оправдание.

## Скрипты проекта

Все запускаются из корня проекта.

| Скрипт | Что делает |
|---|---|
| `backend/scripts/check_setup.py` | проверяет окружение: пакеты, конфигурацию, наличие артефактов |
| `backend/scripts/generate_dataset.py` | генерирует датасет на 100 000 транзакций и валидирует его |
| `backend/scripts/train_model.py` | обучает модель, печатает метрики, сохраняет артефакт |
| `backend/scripts/evaluate_risk_engine.py` | печатает оценку порогов и политик на реальном потоке |
| `backend/scripts/export_evaluation.py` | выгружает ту же оценку в `backend/models/evaluation.json` для дашборда |
| `backend/scripts/export_features.py` | генерирует [docs/FEATURES.md](docs/FEATURES.md) из реестра признаков |
| `backend/scripts/export_hand_testing.py` | генерирует [docs/HAND_TESTING.md](docs/HAND_TESTING.md) прогоном сценариев |
| `backend/scripts/check_docs.py` | сверяет README с кодом и артефактами |

### Почему часть документации генерируется

`docs/FEATURES.md` и `docs/HAND_TESTING.md` собираются скриптами, а не пишутся
руками. Причина практическая: рукописная таблица расходится с кодом после
первого же переобучения модели — и начинает врать ровно там, где её читают
внимательнее всего.

README генерировать нельзя, это связный текст. Поэтому за ним следит
`check_docs.py`: он сверяет заявленные метрики с артефактом модели, таблицу
сценариев с `HAND_TESTING.md`, упомянутые скрипты с содержимым каталога
и ссылки с файлами на диске.

```bash
python backend/scripts/check_docs.py
```

Скрипт появился не от избытка аккуратности: метрики в README успели устареть
на три переобучения, и заметить это можно было только случайно.

## Возможные улучшения

Список честный: здесь то, чего в прототипе нет, с указанием, почему
без этого можно было обойтись на демонстрации и во что это упрётся
в проде.

**База данных для профилей и истории.** Сейчас они в памяти (раздел
2.3). Растут линейно с числом клиентов, а память контейнера — нет,
поэтому в проде переезжают первыми. Интерфейс хранилищ отделён от
сервисов именно ради этого: менять придётся четыре класса в
`backend/app/store/`, а не цепочку обработки.

**Учётные записи вместо общего пароля.** Запись конфигурации закрыта
одним `CONFIG_ADMIN_TOKEN`. Он не различает людей и не отзывается
по одному — это закрытая дыра, а не решённая задача доступа
(см. D-20 в [docs/TZ.md](docs/TZ.md#отклонения-и-решения)). Нужны
учётные записи, роли и журнал действий: кто, когда и какой порог
подвинул.

**Переобучение на метках аналитика.** Метки собираются и хранятся
как датасет — со слепком решения, а не как журнал кликов. Но цикл
пока разомкнут: переобучение запускается руками скриптом. Замкнуть
его — значит добавить расписание, сравнение новой модели со старой
на отложенной выборке и отказ от выкатки, если она хуже.

**Списки риска от провайдера: страны и VPN.** Оба зашиты константами.
В проде и то и другое приходит от провайдера риск-данных и обновляется
без выкатки.

С VPN оговорка сильнее. Настоящие базы адресов VPN, прокси и хостинга
(MaxMind, IPQualityScore) платные и обновляются ежедневно; здесь же
десяток диапазонов, которыми пользуется и генератор датасета. На
синтетических данных признак честный, на настоящих адресах он не
распознает ничего, кроме этих десяти диапазонов. Это прототип
механики, а не детекция.

Сам по себе VPN и не улика: им пользуются в поездках, в офисах и просто
из осторожности. В обучающих данных он есть у 41 % мошеннических
операций и у 3 % обычных, а среди всего VPN-трафика мошеннических
лишь каждая пятая — поэтому модель и не опирается на него одного.

**Очередь для потока.** Прототип синхронный: «ввёл транзакцию —
увидел решение». Пакетная обработка есть (`POST /predict/batch`),
но при настоящем потоке между приёмом и обработкой нужна очередь,
иначе всплеск нагрузки упирается в таймаут HTTP.

**Правки конфигурации переживают перезапуск.** Сейчас они живут
в памяти, и рестарт возвращает к `.env`. Для демонстрации это
достоинство — неудачную правку отменяет перезапуск, а не поиск того,
кто её сделал. В проде понадобится хранение с историей и возможностью
откатиться к конкретной версии.

**Формулировки причин на трёх языках.** Всё остальное переведено
параметром `?language=`, включая текстовый отчёт. Английскими остаются
формулировки причин из XAI и названия политик: ТЗ §7 задаёт их
по-английски, и это официальная формулировка системы — перевести их
значило бы завести вторую версию того же утверждения. Развязать это
можно, но тогда английский вариант должен остаться доступным
как `?language=en`, а не исчезнуть.

**Дрейф по меткам, а не только по признакам.** Сейчас система видит,
что распределение входных данных уехало. Чего она не видит — что уехало
качество: для этого нужны метки в темпе потока, а их даёт только
аналитик.
